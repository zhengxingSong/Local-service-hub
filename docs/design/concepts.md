# 服务中枢 — 概念模型（讨论稿）

> 骨架来自用户：**配置（三类形态各自的闭环 + 配置本身的闭环）→ 看见配置并管理（CRUD）→ 运行（资源/启动状态/报错日志）→ 预设组（多服务一键拉起 + 整套 CRUD）**。
> 本文在该骨架上补全。凡属补全的内容都标了 **[补]**，便于分辨哪些是我加的。

---

## 0. 五层概念（先把名词定死）

```
用途 Purpose          用户真正想用的东西：OpenViking 检索 / 27B 聊天 / WeKnora 知识库 / Rerank
  ↑ 由…实现
组 Group              用途的实现：一组**有序**的配方，一起启停，可标记独占          [补：有序]
  ↑ 成员是
配方 Recipe           一份可无歧义重放的启动定义（用户口中的"服务配置"）
  ├ 形态 Form         compose / source / model（用户说的三类）
  ├ 准备 Provision    拉镜像·构建 / 装依赖 / 取模型        [补：这一层是三类形态真正的差异]
  ├ 启动 Launch       compose up / spawn / llama-server
  ├ 暴露与就绪        端口 / alias / 判定方式
  ├ 需求 Requirement  环境·资源·占用·依赖声明（用于预检）
  └ 策略 Policy       启用 / 自启 / 归属组 / 独占
  ↑ 实例化
实例 Instance         配方的当下：状态机 + 进程或容器 + 实测资源 + **运行记录**   [补：运行记录]
  ↑ 消耗
账本 Ledger           显存 / RAM / CPU / 磁盘 / 端口
```

**关键判断**：用户脑子里的对象是"OpenViking"，不是"OpenViking 组"。组是手段，用途是目的。所以
1. **组的名字就是用途的名字**（OpenViking、WeKnora），不要出现"组 1"；
2. 运行态按**用途**呈现；
3. 单服务用途 = 只有一个成员的组（用户配置里的 rerank / weknora / laya 就是这种）。

## 1. 配置

### 1.1 三类形态的差异不在"启动"，而在"准备" **[补]**

你提到"不同服务有不同的闭环"。把三类摆在一起看，**启动动作其实是一样的**（拉进程 / `compose up` / 起 llama-server），真正的差异全在"启动之前要准备什么"：

| 段 | compose（docker 应用） | source（源代码部署） | model（模型服务） |
|---|---|---|---|
| 识别 | 目录里有 `compose.yml` | 目录里有入口脚本 | 文件是 `.gguf` |
| **准备** | `pull` 拉镜像 / `build` 构建 | **装依赖**（pip / uv / R library / go build） | 取模型文件 + 校验（大小 / SHA256） |
| 启动 | `compose up -d` | spawn 可执行文件 | llama-server + 模型 + 参数 |
| 暴露与就绪 | 端口 / HTTP | 端口 / HTTP | 端口 / `openai-models` alias |
| 需求来源 | **读** compose（ports / mem_limit / volumes）+ 声明 | **声明** + 实测回填 | **算**（GGUF + ctx/parallel/ngl）+ 实测回填 |

由此得出一条结构性结论：**统一"启动"，分离"准备"。** 配方里应当有一个可选的**准备步骤**，与启动步骤并列。

- 没有它，"源代码部署"这个词是落不了地的——现在应用只能执行一个命令，装虚拟环境、装依赖、编译都得你自己先在外面做好，那就等于没有"部署"。
- 没有它，模型服务的"模型文件从哪来"也不在配置的闭环里。
- compose 的准备可以省略（`up` 会自动拉镜像），但显式准备能提前暴露"镜像拉不动"，并且让长耗时动作与"启动"分离。

于是配方多出一个状态位：**未准备 / 已准备**（见 §3 的状态位）。

### 1.2 配置自身的闭环 **[补：判据不是"保存成功"**

```
探测（这是什么东西？） → 填写/确认 → 校验（字段 + 可执行性） → 准备（可选） → 试运行 → 保存 → 落入清单
                                                                          ↑
                                                            这一环才是判据，不是"保存成功"
```

- **探测**：系统先自己看出形态（有 `compose.yml` / 有 `requirements.txt` / 有 `.gguf`），而不是先让你从三个单选框里选。
- **校验**：字段合法性 + 路径存在 + 端口合法 + **预检四族**（依赖 / 环境 / 占用 / 资源）。
- **准备**：可单独执行（"准备好但先不启动"），幂等、可取消、可重试。
- **试运行**：真的起一次，确认能就绪；同时把实测资源回填账本、把就绪判定是否有效也验证掉。
- **闭环判据：试运行通过。** 用户最怕的是"保存成功但跑不起来"。

### 1.3 CRUD 的三个副作用必须显式 **[补]**

| 动作 | 副作用 |
|---|---|
| 改（Update） | 正在运行时：**先停 → 改 → 再起**（必须先等进程真正退出，否则新配置会被旧进程冒充）；改端口/形态可能影响依赖它的组 |
| 删（Delete） | 运行中要先停；**从所有组里摘掉**（否则组里留悬空成员）；被别的配方依赖时给出提示 |
| 复制（Duplicate） | 同类配置复用（配好一个 llama 服务后，再配一个只需改模型与端口）——实际使用中高频，不能只有"新建" |

### 1.4 配置的完整动作清单

新建（探测）· 试运行 · 保存 · 编辑 · **复制** · 删除 · 启用/禁用 · 设自启 · **准备** · 查看详情 · 查看日志 · 查看运行记录 · 打开所在目录（compose 目录 / 工作目录）· **导出配方**

## 2. 看见配置并管理（CRUD 闭环）

你说的"可视化 + 后续修改"，在概念上是**同一对象的两种深度**，不是两个东西：

- **清单层（默认）**：一行一个配方，显示的是**定义视角**的信息——名称 / 形态 / 暴露（端口或 alias）/ 归属组 / 启用·自启 / 准备状态 / 最近一次运行的结果（成功/失败/从未运行）。
- **详情层（展开）**：完整字段（按形态不同）、需求声明、就绪判定、实测资源、日志、运行记录、以及全部动作入口。

**[补] 清单不显示实时运行状态**，只留一个极简状态点作为导航锚点。理由是：实时状态是运行态的职责，若两边都表达，就会出现两份"同一批东西"的列表，互相污染——这正是"信息密度大却没有重点"的成因之一。

## 3. 运行

### 3.1 三个状态位必须分开表达 **[补：这是最容易混淆的地方]**

现在配置里有 `enabled` 与 `autostart`，实例里有 `state`，但界面把它们混在一处，于是"我启用了它"和"它正在跑"分不清。必须显式区分：

| 状态位 | 含义 | 归属 |
|---|---|---|
| `enabled` | 配置上**允许**被启动 | 配置 |
| `autostart` | 随**应用启动**自动拉起 | 策略 |
| `prepared` | 准备是否已完成（镜像/依赖/模型就位） | 准备 |
| `state` | 此刻的实例状态：`stopped / starting / loading / ready / failed / restarting` | 运行 |
| 组的 `n/m` | 成员就绪数与失败数 | 运行（组级） |

### 3.2 运行态要看见的三件（你列的）+ 补全

| 你列的 | 补全 |
|---|---|
| 当前资源使用 | **按"还能启动什么"组织**，而不是按曲线：余量 + 占用者 + 冲突。它是预检的可视化，不是监控仪表盘 |
| 当前服务的启动状态（启用了哪些） | 分两层：**用途/组层**（OpenViking 3/4 就绪、聊天组可用）+ **成员层**（单个服务启停）。并且明确区分上面五个状态位 |
| 报错信息与日志，好溯源 | **溯源需要三层，不是一层**：①错误归因（哪一族条件、哪个阶段）②运行记录 ③日志文本 |

### 3.3 溯源的三层 **[补：第二层现在是缺的]**

1. **错误归因**：属于哪一族条件（依赖/环境/占用/资源）、属于哪个阶段（准备失败 / 启动失败 / 就绪超时 / 运行中崩溃）。
2. **运行记录（Run Record）**：每次运行的开始时间、结束时间、退出码、是否被手动停止、崩溃重启第几次、**就绪耗时**（模型加载要多久）、启动时与峰值的资源占用。
   - 现在只有一个内存里的 `restartCount`，应用一重启就丢；日志文件又只有文本。于是"它今天为什么重启了三次""上次什么时候失败的""模型加载要多久"都答不出来。
   - **这是溯源真正的基础设施**，建议持久化最近 N 条。
3. **日志**：尾部文本（已有）+ 打开日志目录（已有）。

## 4. 预设组

### 4.1 组的完整概念 **[补]**

| 属性 | 说明 |
|---|---|
| 名称 | **就是用途名**（OpenViking / WeKnora），不是"组 1" |
| 成员 | 有序的配方 id 列表 |
| 顺序与就绪等待 | **[补]** 顺序不是装饰：ov-server 必须先等 embedding / intent 就绪才连得上 |
| 独占 | 启动时与其它独占组互斥（显存约束），需先仲裁 |
| 随应用启动 | 组级的 autostart |

### 4.2 组的两层语义 **[补]**

- **第一层：一起启停**（你已经想到的）——一次点击拉起多个，不用一个个点。
- **第二层：按序启动 + 就绪等待**（你没提但真实需要）——先起依赖，等它 ready，再起下一个；停止时逆序。

建议本版只做这两层，**不做跨组的依赖图、不做组的嵌套**。理由：组内有序已经能表达现实需要，而依赖图/嵌套会让资源计算与失败回滚变得无法向用户解释。

### 4.3 组的 CRUD 与边界 **[补]**

| 动作 | 语义 |
|---|---|
| 新建 / 改名 | 改名不影响成员 |
| 增删成员 / 调整顺序 | 顺序即启动与停止序 |
| 标记独占 / 取消 | 影响启动时是否需要仲裁 |
| **删除组** | **只解散组合，不删任何服务**（必须显式说明，否则用户不敢删） |
| 成员被删除 | 自动从组里摘掉，并提示 |
| 成员被禁用 | 启动组时**跳过并告知**（不是静默跳过，也不是整组失败） |
| 一键启动 / 一键停止 / 重启整组 | 三种组级操作 |

### 4.4 组的运行状态不是二值 **[补]**

不是"运行中 / 已停止"，而是 **n/m 就绪**（例如 3/4 就绪、第 4 个失败）。有失败成员时是"部分可用"，这必须是一个可见且可操作的状态——否则用户只看到"没起来"，不知道已经有三件在跑、占着资源。

### 4.5 组与资源的关系 **[补]**

组的资源需求 = 成员需求之和；独占组之间互斥。所以**启动组是预检的最大使用者**：它可能一次吃下 18GB 显存，因此"切换组"这个动作必须走完整的四族预检 + 仲裁，而不是简单的批量启动。

## 6. 三个态与上述概念的对应

| 态 | 主体 | 概念范围 |
|---|---|---|
| **配置态** | 配方（按**配方**扁平列出） | 配方 CRUD + 准备 + 试运行 + 组 CRUD + 全局设置 |
| **运行态** | 用途/组（按**用途**分组呈现） | 组与实例的启停、资源账本、状态位、错误入口 |
| **处置态** | 就地展开，不跳页 | 预检四族结论、错误归因、运行记录、日志、修正动作 |

**这两个态的列表分组方式不同（配置态按配方、运行态按用途），因此不是"同一份列表显示两遍"**——这是避免两套模型互相污染的关键。

## 8. 建议直接采纳（如无异议，不再单独确认）

### 8.1 素材（Asset）与账本（Ledger）是两种不同的资源

原来的"资源"把两样东西混在一起了：

| 类别 | 内容 | 特征 | 谁来管 |
|---|---|---|---|
| **账本 Ledger** | 显存 / RAM / CPU / 磁盘 / 端口 | **消耗型**：被占用就少了，停止后归还 | 预检的输入 |
| **素材 Asset** | 模型权重（GGUF）、容器镜像、依赖锁文件 | **被引用型**：可被多个配方共用，不因启动而减少 | 引用的目标 |

为什么必须分开：同一个 GGUF 文件可以被两个不同参数的模型服务引用；同一份镜像可以被多个 compose 引用。因此

- 配方**引用**素材，而不是拥有它；
- 删除素材前必须检查引用（"还有 2 个配方在用它"）；
- 素材有独立的生命周期：**未就位 → 获取中 → 已就位（含校验）→ 损坏 / 过期**。

### 8.2 "试运行"就是通用化的"一键体验"

已有的"一键体验"（临时端口、不写配置、满意后转正）其实就是配置态的**试运行**。两者应当合成同一套机制：

- 配置态里任何配方都可以"试运行" → 产生一个**临时实例**（不写配置）；
- 试运行通过 = 配置闭环的判据；
- 满意则"转正"，**沿用临时实例的实测值**（就绪耗时、资源占用）回填账本，并把配方持久化；
- 不满意则丢弃，不留残条目。

这样 llama 的体验、compose 的试跑、源码的试跑是同一套语义，不需要三套。

### 8.3 运行记录分两条线

| 线 | 粒度 | 回答的问题 |
|---|---|---|
| **Run（每次启动一条）** | 起止、退出码、就绪耗时、资源峰值、是否手动停止、第几次重启 | "这次运行怎么样""模型加载要多久" |
| **Event（状态变化一条）** | 状态迁移、重启、被停止、配置变更、准备失败 | "几点几分发生了什么"（时间线） |

默认保留：每个配方最近 20 条 Run；Event 保留最近 7 天或 2000 条。都是默认值，不是硬约束。

### 8.4 敏感值要引用，不要内联

compose 应用与 OpenViking / WeKnora 这类服务常需要 API key、token、数据库口令。现在它们明文写在 `services.json` 的 `env` 里，等于**明文落盘**。建议：

- 配方里的环境变量支持**引用**（`{{env:NAME}}` 取进程环境变量，或指向一个 `.env` 文件）；
- 界面显示引用名而不显示值；
- 不引入密钥库（那会变成另一个产品），只做"不内联明文"这一步。

### 8.5 配置快照与回滚

`services.json.bak-*` 已经在自动产生，但界面没有回滚入口。既然"改配置"有副作用，就该有退路：列出最近几次快照，一键恢复。低成本，纳入但优先级低于前面几项。

## 9. 明确的边界（本轮不做）

| 不做 | 理由 |
|---|---|
| **热监测 compose 文件与模型文件** | 只监测 `services.json`；compose 文件与模型在**启动时读取**。否则监测范围会无限扩张（镜像 tag、卷、外部依赖），而且"文件变了要不要重启"没有好答案 |
| **组嵌套、跨组依赖图** | 组内有序已能表达现实需要；依赖图会让资源计算与失败回滚无法向用户解释 |
| **多机管理** | `host` 字段继续预留，不实现 |
| **权限 / 多用户** | 本机单用户 |
| **独立密钥库** | 只做到"不内联明文"（见 8.4） |

## 10. 命名约定与三条补充边界

### 10.1 文档用精确概念名，界面用你已经形成的词

| 概念（文档 / 代码） | 界面用词 | 理由 |
|---|---|---|
| Recipe 配方 | **服务** | 你一直说"服务"；"配方"是内部概念，不该出现在界面上 |
| Provision 准备 | 按形态显示具体动作：**拉取镜像 / 构建镜像 / 安装依赖 / 下载模型** | 不强行统一叫"准备"——具体动作才是你能判断的东西 |
| Group 组 | **预设组** | 你的原词 |
| Purpose 用途 | 不引入独立层，组的名字承担用途名（已定） | — |
| Asset 素材 | **模型文件 / 镜像 / 依赖包** | 不要出现"素材"这种抽象词 |
| Ledger 账本 | **资源** | 界面就叫"资源" |
| Instance 实例 | 不出现，直接说"运行中 / 未运行的服务" | — |

原则：**内部概念名求精确，界面文案求熟悉。** 两者不必一致。

### 10.2 一个配方至多一个实例

不支持"同一配方同时起两个实例（换端口跑两份）"——需要两份就用「复制」生成两个配方。这样"服务 ↔ 运行实例"是 `1 : 0..1`，避免"这份配置现在跑着几个"的歧义。

### 10.3 强制启动的结果必须回填

"强制启动（接受降级风险）"之后，要把**实际结果**写进运行记录，并用实测值修正该配方的需求估算。这样预检会一次比一次准；否则"强制启动"只是把问题推给下一次。

### 10.4 不做自动抢占

资源不足时**不自动**停掉低优先级的组来给高优先级的组让路。仲裁永远是显式的、由你确认的。理由：自动抢占会在你不看的时候改变机器状态，而这是本机唯一那份显存。

## 11. 已定的三件事（选项保留作为记录）

- **配方与组**：允许共享，停组时提示 → 选项 A
- **用途层**：不引入独立用途层，组名即用途名 → 选项 A
- **组切换**：是事务，失败回滚 → 选项 A

### 原选项（记录）

1. **一个配方能否属于多个组？**
   现状是允许的（`presets` 是组名 → 服务 id 列表）。但这样"一键停止某组"的语义就模糊了：停掉组 A，会不会连带停掉组 B 也在用的服务？
   A) 允许共享；停组时提示"该服务也被组 B 使用，是否一并停止"（推荐）
   B) 禁止共享：一个配方只能属于一个组（语义最干净，但 rerank 这类被多用途共用的服务会被迫复制）
   C) 允许共享；停组时**只停**没有其它运行中的组需要的成员（自动保留，但用户可能困惑"为什么没停干净"）

2. **是否需要独立的"用途"层？**（组与用途是否 1:1）
   A) 不需要：**组名就是用途名**，保持扁平（推荐）
   B) 需要：一个用途可以绑多个组（例如 OpenViking 分"检索组"和"索引组"），运行态按用途聚合

3. **组切换是否是一个事务（失败要回滚）？**
   切换组的真实过程是"先释放旧档 → 再申请新档"，中间有几十秒窗口。
   A) 是事务：切换期间拒绝其它启动请求；新档启动失败时**回滚**（把让位的旧档恢复）并告知（推荐）
   B) 不是事务：就是"先停一批、再起一批"，失败就失败，用户自己收拾
