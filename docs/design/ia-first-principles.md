## 1. 这个服务满足什么需求

不从功能清单出发，从「用户手里真正要完成的事」出发。

用户有一批**本机能力**（本地模型端点、Python 服务、容器栈），它们被**别的东西消费**（OpenViking 检索、聊天客户端、WeKnora、自己的脚本）。这些能力有三个特征：

1. **启动成本高**：命令行参数多到记不住（chat-27b 有 25 个参数），路径与工作目录绑定本机。
2. **必须按需可用**：消费方不会等你手动去起服务，起晚了就是一次失败调用。
3. **彼此抢同一份稀缺资源**：一张 24GB 卡；27B 大上下文与 OpenViking 三件套不能共存。

所以这个服务满足的需求是：

> **让一组本机能力在我需要它们的时候确定可用，并且不会互相抢资源。**

三个词各自决定了一部分设计：

| 词 | 含义 | 设计后果 |
|---|---|---|
| **确定可用** | 不是「进程起来了」，而是「能力可用了」 | 就绪判定是一等公民，不是附加信息 |
| **一组** | 用户的原子是能力集合，不是单个进程 | 界面主体是组，不是服务清单 |
| **不互相抢** | 资源仲裁是常态，不是例外 | 显存与互斥必须在操作路径上，不能只做警告 |

## 2. 用户在这里做什么（四个问题）

### 启动什么

不是「启动服务」，而是「切到我要用的那件事」。因为能力集合互斥，这本质是**单选档位**，不是多选开关。

两种意图必须分开：

- **临时切一次**（现在就要用，用完可能还要切回去）→ 高频操作，必须是首屏一次点击。
- **常驻**（以后每次开机都要）→ 这是策略，属于配置，不该混进每次操作。

### 注意什么

只有三类，且都指向同一件事——**能力不可用**：

| 类型 | 表现 | 为什么危险 |
|---|---|---|
| 起不来 | 失败态 + 错误摘要 | 能力直接不可用 |
| **起来了但没就绪** | 端口通、模型还在加载、alias 不对 | **最危险**：下游会静默失败，用户以为在用 |
| 资源越界 | 显存不足；或旧档没停净又起新档 | OOM，或静默降级 |

**关键推论：「注意」是事件，不是面板。** 常态下它的信息量恒为零；发生时它必须占据第一视觉。把「注意」做成常驻面板，就是把零信息量的东西挂在最贵的位置上。

### 配置什么

| 层 | 内容 | 频率 |
|---|---|---|
| **装配** | llama-server 路径、模型目录、服务定义、组定义 | 一次性，偶尔调整 |
| **策略** | 崩溃重启上限、显存阈值、登录自启 | 偶发 |
| **临时** | 改端口避让、降 ctx/ngl 省显存、换模型 | 问题驱动 |

**关键推论：装配不是使用态的一部分。** 把「施工」和「使用」混在同一屏，就是「信息密度太大却找不到重点」的根因——它们服务于两种完全不同的心态。

### 看见什么

必须常驻看见的只有三件：

1. **当前档位能不能用**（按能力集合，不按服务计数）
2. **为什么不能用**（可执行的原因，不是错误码）
3. **资源还剩多少**（只在接近上限时才有意义）

不需要常驻看见：每个服务的端口、PID、重启次数、就绪判定方式、日志、显存估算值。这些是**排障时的细节**，按需展开即可。

## 3. 为什么「顶栏摘要」是错的

上一版我提的顶栏摘要（运行 N · 就绪中 N · 失败 N · 显存 X%）有三个错误：

1. **原子错。** 它按服务计数，而用户的原子是能力集合。正确的说法是「OpenViking 可用 / 聊天不可用」，而不是「运行 5 失败 1」。用户不关心有几个进程，只关心他要用的那个能不能用。
2. **时机错。** 它把「注意」做成了常驻面板。一切正常时它恒为「运行 5 · 失败 0」，信息量为零；出问题时它又只有一行小字，弱到看不见。**它把最弱的表现形式给了最重要的信息。**
3. **前提错。** 它假设用户会打开主界面看它。托盘常驻的应用里，用户可能几天不开窗口。该做的是**通知**与**托盘状态**，不是面板。

它唯一正确的地方是：**异常必须在第一视觉里可见**。这一点保留，但载体换成三处——档位卡片的异常态、托盘图标状态、系统通知。

## 4. 工作台：三个态，不是一个页面

「工作台」这个方向是对的，但需要具体化：**工作台不是「把一切摆在一张桌上」，而是「在这里把事做掉」。**

由此得出三个态。它们不是三个标签页（标签页暗示三者地位相等、可以随意来回切），而是三种不同进入条件的状态。

### 运行态（默认，就是工作台）

- **唯一主体：能力卡**。一张卡 = 一个组（能力集合），不是一行服务。
  - 卡上只有：组名、成员就绪数（如 3/4）、可用性状态、主操作、独占标记、出问题时的原因。
  - 主操作是「启用 / 停用」；标记独占的组在启用时自动仲裁（先告知将停哪个档、能释放多少显存）。
- **单成员组**：不在任何组里的服务自动成为单成员能力卡（用户当前配置里的 rerank / weknora / laya），这样运行态不需要第二套模型，也不必在「服务」和「组」之间做选择。
- **资源约束**：显存条常驻但低调，接近阈值时才醒目——因为它是切换档位的约束条件。
- **异常就地**：哪一档出问题，就在那张卡上显示原因与修复动作，不跳页。
- **这里没有**服务清单、端口、PID、参数、日志。

### 处置态（异常驱动，就地展开）

- 从能力卡展开：哪个成员失败或未就绪、错误摘要、日志尾部、三类修正动作（重启 / 编辑 / 停掉占用者或降参）。
- **不做成独立页面**：排障时不能丢掉「其它档位还可用吗」这个上下文。

### 装配态（明确进入、明确退出）

- 全量服务清单（三类形态）、编辑表单、组定义、模型库与下载、设置。
- 一个入口、一个出口；装配完回到运行态。它可以是独立页面（换房间），也可以是同一页的另一种密度。

## 5. 闭环映射的调整

12 个闭环不变，但归属从「按对象」改为「按意图」：

| 态 | 承载的闭环 |
|---|---|
| 运行态 | L2 组切换、L11 资源告警、L10 退出 |
| 处置态（就地） | L1 巡检（异常分支）、L6 排障、L7 日志导出 |
| 装配态 | L3 新增服务、L4 体验转正、L5 下载、L8 设置、L12 组管理 |
| 全局事件 | L9 外部配置变更（提示条）、L10 托盘退出 |

注意 L1「巡检」的性质发生了变化：**在运行态里它不再是一个需要用户主动执行的闭环**——若一切正常，用户不需要「巡检」任何东西；只有异常才把他拉进处置态。这是本稿与上一稿最重要的差别。

## 6. 需要定的岔路

1. **是否「一切皆组」**：运行态只呈现能力卡（含单成员卡），还是同时保留一份服务清单？
2. **装配态的形态**：独立页面（换房间）／同一页的另一种密度（可切换）／首次启动向导 + 之后按需进入？
3. **常态是否「什么都不说」**：只用托盘图标与系统通知承载异常，主界面在没有异常时不显示任何状态汇总？
