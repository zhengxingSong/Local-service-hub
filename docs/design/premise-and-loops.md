# 服务中枢 — 前提、对象模型与使用闭环（第二版，取代 ia-first-principles.md）

> 第一版把需求写成「让一组本机能力确定可用」，那是**消费方视角**（谁在用它）。
> 正确的前提是**提供方视角**：把「让一份东西在本机跑起来并配好」这件事，从写代码/敲命令变成点界面。
> 叠加约束「本地资源有限」，于是**启动前的条件检查**是核心，而不是附属。

## 1. 服务支持什么

| 形态 | 用户手里的东西 | 现状 |
|---|---|---|
| `command` | 源代码目录（Python / R / Go / Node …） | 已支持：可执行文件 + 参数 + 工作目录 + 环境变量 |
| `compose` | docker 应用（compose 文件 + 镜像） | 已支持：`docker compose up -d / down / restart / logs` |
| `llama` | 模型权重（GGUF）+ 推理 runtime | 已支持：llama-server + 模型 + mmproj + 参数 |

这三类不是「三种服务类型」，而是**同一种东西的三种启动方式表达**。真正被管理的东西是**一份待运行的配方**。

## 2. 前提（从用户手里的事出发）

用户的原始处境：拿到一份东西（镜像 / 源码 / 模型），要它在自己的机器上跑起来并能用。他面对三件麻烦：

1. **启动方式记不住**：chat-27b 有 25 个参数；compose 有 profile 与 env；Python 服务有虚拟环境与工作目录。
2. **每份东西的启动方式都不一样**：语言、runtime、依赖、端口、配置文件、就绪信号全不同。
3. **本机资源是有限且共享的**：一份 24GB 显存的卡、一份内存、一份 CPU、一组端口；不同服务要的资源不一样，加起来会超。

所以这个服务满足的需求是：

> **把「让一份东西在本机跑起来」从写代码/敲命令，变成点界面；并且在资源有限的前提下，启动前就知道能不能跑、跑起来会挤掉谁。**

两句话各自决定一半设计：
- 前半句 → **配方（Recipe）是一等对象**，它必须能被无歧义地重放；配置必须能探测、能校验、能立刻试用。
- 后半句 → **资源账本（Ledger）与预检（Pre-flight）是一等对象**，不是监控面板。

## 3. 对象模型

```
Recipe 配方            —— 怎么启动它（一次配好，反复重放）
  ├ 形态与启动定义      command+args+cwd+env | composeDir+file+profiles | llamaServer+model+mmproj+参数
  ├ 暴露与就绪          port / alias / URL / 就绪判定（tcp | http | openai-models | none）
  ├ 需求声明 Requirements
  │   ├ 环境：runtime（docker / python3.12 / llamacpp-bXXXX）、文件、镜像、配置文件
  │   ├ 资源：gpuMB、ramMB、cpuThreads、diskGB
  │   ├ 占用：port、互斥组
  │   └ 依赖：其它配方必须已 ready
  └ 策略               autostart、enabled、重启上限、归属组、是否独占

Ledger 资源账本        —— 本机能给什么（常驻维护）
  ├ GPU：总量 / 已用 / 按服务实测
  ├ RAM：总量 / 已用
  ├ CPU：核数 / 当前负载
  ├ 磁盘：各盘余量（含模型与镜像占用）
  └ 端口：已占用清单及占用者

Instance 运行实例      —— 配方 + 当下状态
  state(stopped | starting | loading | ready | failed | restarting)
  pid / containerId、port、实测资源占用、lastError、日志位置
```

**关键不对称（必须承认，不能假装统一）**：`llama` 形态的资源需求**可算**（GGUF 元数据 + ctx/parallel/ngl 可推算显存），`command` / `compose` 形态**只能声明 + 实测回填**。所以预检的可靠度按形态递减，界面必须如实表达"这是算出来的"还是"这是估计/声明的"。

## 4. 启动条件 = 四族条件的合取

这是本稿的中心。启动前检查不是"显存够不够"这一件事，而是四族条件的合取：

| 族 | 检查内容 | 不满足时的可执行出口 |
|---|---|---|
| **环境** | runtime 是否存在、文件/镜像是否就位、配置文件是否可读 | 给出安装/拉取/定位动作，或指向设置项 |
| **资源** | GPU 显存、RAM、CPU、磁盘余量是否满足该配方需求 | ①释放（停占用者，显示可释放量）②降需（降 ctx/ngl/parallel/线程，给建议值）③换目标（换盘/换 runtime） |
| **占用** | 端口是否空闲、互斥组是否有成员在跑 | 换端口 / 停掉占用者 / 触发互斥仲裁 |
| **依赖** | 该配方依赖的其它配方是否已 ready | 按序先启动依赖，并显示依赖就绪进度 |

**闭环判据**：启动动作要么真的进入启动流程，要么给出**一个用户立刻能做的具体动作**——而不是一句"启动失败"。

## 5. 使用闭环（按对象生命周期与资源约束拆解）

格式仍是：触发 → 感知 → 决策 → 动作 → 反馈 → **闭环判据**。

### L1 纳管：从「一份东西」到「一份配方」
- 触发：我拿到一份要跑的东西（目录 / compose 文件 / GGUF / 一段命令行）。
- 感知：**系统探测**它是什么——有 `compose.yml`？有 `requirements.txt` / `go.mod` / `package.json`？有 `.gguf`？有可执行文件？给出候选形态与已探测字段。
- 决策：确认或修正形态与字段。
- 动作：保存配方（启动定义 + 端口 + 就绪判定 + 需求声明）。
- 反馈：进入"可运行清单"，尚未启动。
- **判据：下一次一键启动不再需要我提供任何信息。**（配方可无歧义重放）

### L2 预检：启动前把四族条件查完
- 触发：我要启动某配方或某组。
- 感知：`Recipe.需求` vs `Ledger + 其它 Instance 的占用`，四族逐项给出结论。
- 决策：满足 → 直接启动；不满足 → 从该族的出口里选（释放 / 降需 / 换目标 / 先起依赖）。
- 动作：执行选择，或明确"强制启动并接受降级"。
- 反馈：进入启动，或给出具体到字段的修正入口。
- **判据：要么进入启动流程，要么给出一个立刻可执行的动作。**

### L3 启动与就绪
- 触发：预检通过 / 用户强制启动。
- 感知：进程或容器存在 ≠ 可用。
- 动作：按该配方的就绪判定确认（端口 / HTTP / 模型列表 alias / 自定义命令）。
- 反馈：`starting → loading → ready`。
- **判据：能力可用（不是进程存在）。**

### L4 资源观察（常驻，但它是决策输入而不是监控）
- 触发：常驻；接近上限时主动提醒。
- 感知：账本余量 + 每个运行实例的实测占用。
- 决策：还能启动什么 / 启动这个会挤掉谁 / 该停谁。
- 动作：就地停止或调整。
- **判据：用户知道"还能启动什么"，并且知道"是它在吃"。**

> 设计结论：资源面**不是仪表盘**。它要回答的是「余量、占用者、冲突」三个问题，而不是画历史曲线。按"能启动什么"组织，而不是按"画得好看"组织。

### L5 停止与释放
- 触发：不用了，或要让位。
- 感知：停止后能释放多少。
- 动作：停止（等进程真正退出、端口真正释放、容器真正 down）。
- **判据：资源真的回到账本里**，而不是"命令已发出"。

### L6 组合与切换（当一件事需要多个配方，或资源互斥）
- 触发：我要用的东西由多个配方组成（如 OpenViking = vlm + embedding + intent + ov-server）；或它们资源互斥。
- 感知：组内成员就绪进度、预计资源占用、与当前运行集合的冲突。
- 动作：一键切换——先释放，再按序启动，逐个等就绪。
- **判据：目标组全部可用，且被让位的组已停净（含端口与资源）。**

### L7 处置：起不来 / 起来不可用 / 越界
- 触发：失败、就绪超时、资源越界、崩溃重启达上限。
- 感知：**错误分类**（环境缺失 / 端口冲突 / 资源不足 / 参数错误 / 依赖未就绪）+ 日志尾部 + **当时的资源快照**。
- 决策：改配方 / 释放资源 / 换目标 / 放弃。
- 动作：就地修正并重试。
- **判据：错误态清空且能力可用。**

### L8 常驻（策略）
- 触发：我希望以后开机它就在。
- 动作：设为随应用启动（并让应用随登录启动），或作为某组成员随组启动。
- **判据：重启机器后它确实起来了。**

### L9 外部变更
- 触发：配方文件（services.json / compose 文件）被外部修改。
- 感知：差异清单。
- 动作：应用（只重启受影响者）。
- **判据：运行状态与文件一致。**

### L10 让位与退出
- 触发：关闭应用，或切换组。
- 动作：决定停谁、留谁。
- **判据：服务状态符合选择，没有残留占用（端口/显存/RAM）。**

## 6. 必须常驻可见 / 必须就地可操作

这是从闭环反推出的**信息与操作清单**，不是页面清单。页面形态在后面再从这些清单推导。

**必须常驻可见**

1. **资源余量**：GPU 显存 / RAM / CPU / 磁盘——按"还能启动什么"组织。
2. **占用者**：谁在吃这些资源，以及是实测还是估算。
3. **可用性**：按"我要用的那件事"聚合（一组或多配方），而不是按进程计数。
4. **启动条件的当前余量**：现在启动目标配方，会通过还是会被什么挡住。

**必须就地可操作**

启动 / 停止 / 重试；释放（停占用者，并显示能释放多少）；降需（改 ctx/ngl/parallel/线程，给建议值）；改配方（端口、路径、环境、参数）；看日志（尾部 + 打开目录）；设为常驻；把配方编成组并标记互斥。

## 7. 三态与预检的位置

用户已确认的三态，按上面的闭环归属为：

| 态 | 承载的闭环 | 本质 |
|---|---|---|
| **配置态** | L1 纳管、L8 常驻策略、配方编辑与需求声明、组定义 | 施工：把一份东西变成可重放的配方 |
| **运行态** | L2 预检、L3 启动与就绪、L4 资源观察、L5 停止释放、L6 组合切换 | 使用：让配方跑起来，并知道资源账 |
| **处置态** | L7 处置、L9 外部变更、L10 让位与退出 | 修与收尾：归因、修正、释放 |

**结构上最重要的一点：预检（L2）是配置态与运行态的接缝。** 它读配方（配置态的产物）、读账本（运行态的输入）、并决定"能不能进入运行"。把它做成错误提示（现状）还是做成一个决策面（应有），是这版设计的分水岭。

## 8. 已定决策

| 决策 | 结论 |
|---|---|
| **资源需求来源** | 混合：`llama` 算（GGUF + 参数推算）、`compose` 读（`mem_limit` / `ports` / `volumes`）、其余（源码启动）由用户声明；启动后**实测回填**账本；界面**标注可信度** |
| **预检不通过时** | **阻断** + 三条出口（释放 / 降需 / 换目标）+ 显式保留「强制启动」口 |
| **资源面粒度** | 余量 + 占用者 + 冲突。**不做历史曲线**——它是预检的可视化，不是监控仪表盘 |

## 9. 预检决策面的内容契约

固定**四族顺序，从最便宜可修到最贵可修**，每族给出「结论 + 依据来源 + 可执行动作」：

| 顺序 | 族 | 结论示例 | 依据来源 | 可执行动作 |
|---|---|---|---|---|
| 1 | **依赖** | 「需要 embedding 已就绪，当前未启动」 | 配方声明 | 按序启动依赖，并显示依赖就绪进度 |
| 2 | **环境** | 「未找到 python3.12」／「模型文件不存在」／「镜像未拉取」 | runtime 探测、文件与镜像检查 | 安装 / 拉取 / 定位文件 / 直接跳到设置项 |
| 3 | **占用** | 「端口 1933 被 pid 8640 (python) 占用」／「聊天组正在运行，需先释放 18.4 GB」 | 端口表 + 运行实例 | 换端口（给建议值）/ 停占用者 / 触发互斥仲裁 |
| 4 | **资源** | 「需要 8.4 GB 显存，剩余 3.1 GB，差 5.3 GB」 | 算 / 读 / 声明（**标注是哪种**） | 释放（列出候选与可释放量）/ 降需（给建议参数值）/ 换目标（换盘、换 runtime） |

末尾固定一个「**强制启动（接受降级风险）**」——它不是反悔按钮，而是承认预检可能过于保守的出口。

**排序原则**：从最便宜可修到最贵可修，让用户从上往下修；每修一项即重新预检，而不是让用户自己记住还差什么。

**可信度标注（必须做）**：每一条资源结论都要标明是「算出来的」（llama 类，可复算）、「读出来的」（compose 声明）、还是「声明的 / 估计的」（源码启动）。把三者混在一起显示，比不做预检更危险——因为用户会按最可信的那种去相信它。
