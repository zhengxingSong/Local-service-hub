# 服务中枢 — 三态的信息面与操作面

> 上游：[concepts.md](concepts.md)（概念模型）、[premise-and-loops.md](premise-and-loops.md)（前提与闭环）。
> 本文只定**结构**：每个面承载什么信息、有哪些动作、反馈落在哪里、怎么进出。不定视觉。
> **"面（Surface）"不等于页面**——它是一个"有进入条件与承载内容的信息容器"，两个面可以并置，也可以互斥。

## 0. 三态的定义与进入条件

| 态 | 意图 | 进入条件 | 离开 |
|---|---|---|---|
| **运行态** | 让服务跑起来，并知道资源账 | **默认**；或从处置态退回 | 显式进配置态；退出应用 |
| **处置态** | 修与收尾 | **异常发生时自动就地出现**（不改变所在位置）；或用户点开错误 | 错误清空后自动收起 |
| **配置态** | 把一个东西变成可重放的服务 | **显式入口**（"管理服务"）；或首次启动尚无任何服务时自动进入 | 显式退出，回到运行态 |

**结构判断一：处置态不是一个页面，而是运行态的一个就地展开层。**
排障时最不能丢的上下文是"其它用途还可用吗"。跳页去修，等于把这个上下文扔掉。

**结构判断二：三态的区分靠"意图 + 进入条件"，不靠"页面数"。**
所以本文不回答"几个页面"，只回答"有哪些面、谁和谁可以并置"。

## 1. 运行态的信息面

运行态只常驻两样东西：**用途卡**与**资源余量**。

### B1 用途卡列表（常驻，主体）

| 项 | 内容 |
|---|---|
| 进入 | 默认 |
| 承载 | 每个预设组一张卡：组名（即用途名）· 成员就绪 `n/m` · 可用性（可用 / 部分可用 / 切换中 / 未运行）· 独占标记 · 异常原因（若有）· 主操作（启用 / 停用）· 随应用启动标记 |
| 单服务用途 | 不属于任何组的服务自动呈现为单成员卡，运行态因此不需要第二套模型 |
| 可用动作 | 启用 / 停用 / 重启整组 · 展开成员 · 编辑组定义（进配置态）· 看异常详情（进处置层） |
| 反馈落点 | Toast（已启用 / 已停止 / 失败原因）；组级进度就地显示在卡上 |
| 离开 | 展开成员（就地）；点异常（就地展开处置层）；进配置态 |

### B2 资源面（常驻，次要但不可省）

| 项 | 内容 |
|---|---|
| 承载 | 余量（显存 / RAM / CPU / 磁盘）· 占用者（谁在吃，实测还是估算）· **冲突预测**（"现在启动 X 会挤掉谁 / 还差多少"） |
| 为什么不是仪表盘 | 它回答的是"还能启动什么"，不是"过去一小时曲线长什么样" |
| 可用动作 | 释放（停占用者，显示可释放量）· 降需（改参数并重启）· 跳到该占用者的详情 |
| 反馈落点 | 余量数字即时变化；释放动作给 Toast |

### B3 成员明细（就地展开，不独立成面）

| 项 | 内容 |
|---|---|
| 进入 | 展开某张用途卡 |
| 承载 | 该组成员逐行：服务名 · 成员状态位（`enabled` / `prepared` / `state`）· 端口 · 就绪判定结果 · 实测资源 · 失败原因 |
| 可用动作 | 单服务 启动 / 停止 / 重启 · 看实例详情与日志（处置层）· 跳配置态编辑 |
| 为什么就地 | 只想知道"谁拖了后腿"时，不该换一个地方 |

### B4 预检面（**条件性出现**）

| 项 | 内容 |
|---|---|
| 进入 | 任何启动 / 启用 / 切换动作之前 |
| **通过时** | **不出现**。静默检查，直接进入启动；只在 Toast 里说一句"已启动"。这是防止"每次启动都被拦一下"的关键 |
| **不通过时** | 展开为决策面：四族逐项结论（依赖 → 环境 → 占用 → 资源，从最便宜可修排到最贵可修）+ 每族的可执行出口 + 末尾「强制启动（接受降级风险）」 |
| 可信度标注 | 每条资源结论标明：算出来的 / 读出来的 / 你声明的 |
| 可用动作 | 释放 · 降需 · 换目标 · 先起依赖 · 强制启动 · 取消 |
| 反馈落点 | 修一项即重新预检；通过则收起并进入 B5 |
| 离开 | 通过 → 启动；取消 → 回到来源 |

### B5 切换进度（就地状态，不是独立面）

| 项 | 内容 |
|---|---|
| 承载 | 事务化切换的实时阶段：正在停谁 → 等谁释放资源 → 正在起谁 → 第几个就绪 |
| 失败时 | 就地显示回滚过程（"新档启动失败，正在恢复被让位的 X 组"），完成后给结论 |
| 为什么不做成独立面 | 它是"一次操作的过程"，属于被操作的那张卡 |

## 2. 配置态的信息面

配置态是一个**有明确进出口的房间**，主体是"服务"（内部概念：配方）。

### A1 服务清单（常驻，主体）

| 项 | 内容 |
|---|---|
| 承载 | **定义视角**，不是实时状态：名称 · 形态（docker 应用 / 源代码部署 / 模型服务）· 暴露（端口或 alias）· 归属组 · 启用 · 随应用启动 · **准备状态**（未准备 / 已准备）· 最近一次运行结果（成功 / 失败 / 从未运行） |
| 刻意不显示 | 实时运行状态（那是运行态的职责）。只留一个极简状态点作为导航锚点，避免同一批东西出现两份列表 |
| 可用动作 | 新建（探测）· 复制 · 编辑 · 删除 · 禁用/启用 · 设随应用启动 · 准备 · 试运行 · 看详情 · 看运行记录 · 打开所在目录 · 导出 |
| 反馈落点 | Toast（已保存 / 试运行结果）；行内就地显示"准备中 / 准备失败" |

### A2 服务详情 / 编辑（清单的深度，同一个对象）

| 项 | 内容 |
|---|---|
| 进入 | 点 A1 的一行 |
| 承载 | 六段结构：**形态** · **准备**（拉取镜像 / 构建镜像 / 安装依赖 / 下载模型）· **启动** · **暴露与就绪** · **需求**（四族声明 + 可信度）· **策略**（启用 / 自启 / 归属组 / 独占） |
| 可用动作 | 保存 · 准备 · 试运行 · 导出 · 查看运行记录 · 打开所在目录 · 删除 |
| 反馈落点 | 字段级校验就地；试运行结果 Toast + 运行记录里留一条 |

**结构判断三：配置态的"详情"与运行态的"实例详情"是同一个对象的两个页面。**
用同一个容器承载，从 A1 进入默认看"定义"，从 B3 进入默认看"运行"。这样避免"配置详情"和"实例详情"变成两套互相矛盾的东西。

### A3 组定义（预设组 CRUD）

| 项 | 内容 |
|---|---|
| 承载 | 组名（用途名）· 成员多选 · **成员顺序**（即启动与停止序）· 独占标记 · 随应用启动 |
| 边界行为 | 删除组 = 只解散，不删服务（必须显式说明）· 成员被删时自动摘除并提示 · 成员被禁用时启动组**跳过并告知** |
| 可用动作 | 新建 · 改名 · 增删成员 · 调顺序 · 标记独占 · 删除（只解散） |

### A4 素材（模型文件 / 镜像 / 依赖包）

| 项 | 内容 |
|---|---|
| 为什么需要独立面 | 素材是**被引用型资源**：同一个 GGUF 可被多个服务引用，同一份镜像可被多个 compose 引用。它有自己的生命周期：未就位 → 获取中 → 已就位（含校验）→ 损坏 / 过期 |
| 承载 | 名称 · 类型 · 位置 · 大小 · 校验状态 · **被几个服务引用**（引用计数） |
| 可用动作 | 获取（下载 / 拉取 / 定位）· 校验 · 删除（**先检查引用**）· 查看引用它的服务 |
| 与准备段的关系 | A2 的"准备"段执行的动作，作用对象就是这里的东西 |

### A5 设置（全局）

| 项 | 内容 |
|---|---|
| 承载 | llama 能力（runtime 路径 / 扫描根 / 模型目录）· 运行策略（重启上限 / 资源告警阈值 / 登录自启）· 数据位置（配置文件 / 日志目录 / 打开）· **配置快照与回滚** |
| 可用动作 | 修改并保存 · 打开日志目录 · 回滚到某个快照 |

## 3. 处置态的信息面

处置态是**从异常就地展开的一层**，四个面共用一次展开。

### C1 归因面

| 项 | 内容 |
|---|---|
| 承载 | **哪一族条件**（依赖 / 环境 / 占用 / 资源）+ **哪个阶段**（准备失败 / 启动失败 / 就绪超时 / 运行中崩溃）+ 该阶段的原始错误摘要 |
| 为什么要分两维 | "起不来"和"起来了但不可用"的修法完全不同；不归因就只能给一句"启动失败" |

### C2 日志面

| 项 | 内容 |
|---|---|
| 承载 | 日志尾部（自动刷新，仅可见时）· 打开日志目录 · 清空 |
| 与 C3 的分工 | 日志是**原始文本**；记录是**结构化事实**（几点开始、多久就绪、退出码多少、第几次重启） |

### C3 记录面（Run + Event）

| 项 | 内容 |
|---|---|
| Run 列表 | 每次运行一条：起止 · 退出码 · 是否手动停止 · 崩溃重启第几次 · **就绪耗时** · 启动与峰值资源 |
| Event 时间线 | 状态迁移 · 重启 · 被停止 · 配置变更 · 准备失败 |
| 回答的问题 | "它今天为什么重启三次""上次什么时候失败的""模型加载要多久" |

### C4 修正入口

| 项 | 内容 |
|---|---|
| 承载 | 按归因结果给出**具体动作**，而不是通用按钮：改需求（降 ctx / ngl / 线程，给建议值）· 释放（停占用者，显示可释放量）· 改服务（跳到 A2 并聚焦出错字段）· 重试 · **强制停止（清残留）** |
| 反馈落点 | 就地更新状态；成功后处置层自动收起 |

## 4. 浮层策略（三态不是三页，靠的就是这个分工）

| 浮层 | 职责 | 具体用在 |
|---|---|---|
| **内联条** | 不打断的持续状态或提示 | 外部配置变更提示 · 资源告警 · 组切换进度 |
| **就地展开** | 保上下文地深入一层 | 处置层（C1–C4）· 组成员明细（B3） |
| **抽屉** | 单个对象的详情（同一对象两个页面） | 服务详情：定义（A2）与运行（实例 + 日志 + 记录） |
| **模态** | 必须打断的确认与决策 | 破坏性确认（删服务 / 删组 / 退出）· 组切换的独占仲裁 · **预检不通过时的决策面** · 新建服务的第一步（探测结果确认） |
| **Toast** | 所有动作的结果 | 已启动 / 已停止 / 已保存 / 准备完成 / 试运行结果 / 失败原因 |

**结构判断四：只有"必须打断"的才用模态。**
预检**通过**时绝不出现模态（否则每次启动都被拦一下）；不通过时才用模态，因为此时确实需要你做一个选择。

**结构判断五：日志不配独立页面。**
绝大多数日志访问源于"某个服务出了问题"，它天然属于从对象展开的处置层。跨服务时间线是增强项，将来可作为 C3 的一种视图加进来，而不需要新增面。

---

## 5. 刻意没有的面（防止结构漂移）

| 不设的面 | 原因 |
|---|---|
| 总览 / 仪表盘 | 资源面（B2）就是它的全部内容；再单列一个只会重复 |
| 运行态里的"服务清单" | 运行态按用途，配置态按服务；两处都列就会出现两份同一批东西 |
| 独立的日志页 | 见结构判断五 |
| 独立的"预检页" | 预检是条件性出现的面，不是可以随时进去逛的地方 |
| 独立的"任务队列/进度页" | 长动作（准备、下载、切换）的进度属于发起它的那个对象或那条内联状态 |

---

## 6. 跨态一致的三件事

1. **状态位表述一致**：`enabled`（配置上允许）/ `autostart`（随应用启动）/ `prepared`（素材就位）/ `state`（此刻运行态）在三个态里都用同一套词，只是强调的位不同——配置态强调前三位，运行态强调最后一位。
2. **服务 ↔ 实例是 `1 : 0..1`**：界面上不出现"这份配置跑着两个"的说法；要两份就复制成两个服务。
3. **动作结果一律走 Toast，状态一律就地更新**：不用"重新加载页面"来表达成功。
