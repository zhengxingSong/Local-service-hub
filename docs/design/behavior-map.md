# 二、闭环清单

闭环 = 「触发 → 感知 → 决策 → 动作 → 反馈 → **判据**」。判据必须是**可观察的状态**，不是"命令已发出"。

## 2.1 服务对象（7 个）

| 闭环 | 触发 | 关键动作 | 判据 |
|---|---|---|---|
| **C1 纳管** | 我拿到一份东西 | 探测 → 确认形态 → 填必填 → 保存 | 下次一键启动**不再需要我提供任何信息** |
| **C2 准备** | 素材/依赖未就位 | 执行准备（拉取/构建/安装/下载） | 素材变为**已就位且校验通过**；失败时错误可归因、可重试 |
| **C3 试运行→转正** | 想先试试 | 起临时实例 → 试用 → 转正或放弃 | 临时实例消失，被持久服务替代，且**参数与实测值被沿用** |
| **C4 启动与就绪** | 点启动 | 预检 → 拉起 → 等判定 | **能力可用**（不是进程存在） |
| **C5 停止与释放** | 不用了 | 停止 → 等退出与端口释放 | **资源真的回到账本** |
| **C6 编辑生效** | 改配置 | 保存 → 停 → 改 → 起 | 新参数**真的在跑**（不是界面显示新参数） |
| **C7 删除** | 不再需要 | 停 → 从所有组摘掉 → 移除配置 | 清单里没有它，且**没有任何组留悬空成员** |

## 2.2 用途/组对象（4 个）

| 闭环 | 触发 | 关键动作 | 判据 |
|---|---|---|---|
| **C8 组切换（事务）** | 切到另一个用途 | 预检 → 仲裁确认 → 停旧档 → 等释放 → 起新档 → 逐个等就绪 | 目标组**全部可用**，且被让位的组**已停净**；失败则**已回滚** |
| **C9 组定义维护** | 调整组合 | 增删成员/调顺序/标记独占 → 保存 | 组条与运行表现**与定义一致**；成员被删不会留悬空 |
| **C10 部分可用修复** | 组里有人挂了 | 处置 → 修正 → 就地重试该成员 | 组从 `n/m` 变为 `m/m` |
| **C11 共享成员停组** | 停一个被多组引用的组 | 提示共用者 → 由我决定是否一并停止 | 停完后**没有我正在用的用途被意外断开** |

## 2.3 资源对象（2 个）

| 闭环 | 触发 | 关键动作 | 判据 |
|---|---|---|---|
| **C12 资源裁决（预检）** | 任何启动/切换前 | 四族逐项 → 阻断 → 三条出口 | 要么**真的进入启动**，要么给出**一个立刻能做的动作** |
| **C13 释放与降需** | 余量不足 | 停占用者 / 降参数 / 换目标 | **余量数字确实变化**，目标可启动 |

## 2.4 素材对象（1 个）

| 闭环 | 触发 | 关键动作 | 判据 |
|---|---|---|---|
| **C14 素材获取** | 未就位或损坏 | 下载/拉取/定位 → 校验 | **校验通过**且被引用它的服务能用；删除前引用计数为 0 |

## 2.5 环境与全局（4 个）

| 闭环 | 触发 | 关键动作 | 判据 |
|---|---|---|---|
| **C15 外部配置变更** | 文件被外部改 | 提示 → 差异 → 应用 | 运行状态与文件**一致**，且未变的服务**没有被无故重启** |
| **C16 设置维护** | 改全局项 | 保存 | **重启应用后仍成立** |
| **C17 快照回滚** | 配置改坏 | 选快照 → 恢复 | 配置回到该快照，且**回滚前已自动存一份** |
| **C18 退出** | 关应用 | 确认停/留 → 退出 | 服务状态**符合我的选择**，无残留占用 |

**合计 18 个闭环**（原 10 个 + 新结构带出的 8 个）。

# 三、视觉重点

原则：**颜色只用于状态与危险，不用于装饰**；同一状态位在三态用同一个词、同一个色；数值一律等宽（tabular）。

## 3.1 运行态

| 层级 | 内容 | 理由 |
|---|---|---|
| **第一视觉** | 用途卡的**可用性**（整卡左侧色条 + 状态词，不是小圆点） | 我打开它是想知道"我要用的那件事能不能用" |
| **第二视觉** | **异常原因**（内联块，必须可点进处置） | 异常是唯一需要我立刻决策的东西 |
| **第三视觉** | **资源余量与可启动清单**（右侧） | 它是切换用途的约束条件 |
| **按需** | 成员就绪计数、端口、实测占用、就绪判定结果 | 只想知道"谁拖后腿"时才需要 |
| **必须跳出来** | ①有失败成员的卡 ②资源超阈值 ③切换中的卡 | 这三件不能靠我自己发现 |
| **绝不抢视线** | 形态徽标、别名、pid、重启次数 | 查证用，不是扫视用 |

## 3.2 配置态

| 层级 | 内容 |
|---|---|
| **第一视觉** | 服务名 + 形态（"我配了什么"） |
| **第二视觉** | 状态位徽标组（`已启用 / 已准备 / 最近结果`）——它是"这份配置能不能跑"的答案 |
| **第三视觉** | 归属组 · 暴露（端口/别名） |
| **必须跳出来** | **未准备 / 准备失败 / 最近失败** 三态 |
| **绝不抢视线** | 端口号、别名的具体值 |

## 3.3 处置态

| 层级 | 内容 |
|---|---|
| **第一视觉** | **归因结论**：族 + 阶段，一句话可判断 |
| **第二视觉** | **按归因给出的修正动作**（1–3 个） |
| **第三视觉** | 日志尾部（原始证据） |
| **第四** | 运行记录（结构化事实） |
| **必须跳出来** | 那个"能修"的动作——否则我会去读日志而不是去修 |

## 3.4 预检面

| 层级 | 内容 |
|---|---|
| **第一视觉** | **被挡住的那一族**（无问题的族折成一行"✓ 无问题"） |
| **第二视觉** | **差值**（差 16.2 GB）与**占用者身份**（端口 1933 被 pid 8640 / python 占用） |
| **第三视觉** | 该族的出口按钮 |
| **必须跳出来** | 从最便宜可修到最贵可修的**顺序本身**——它决定我从哪里开始 |

## 3.5 三态一致的视觉规则

1. 状态色只有五种语义：可用 / 进行中 / 警告 / 失败 / 未激活。不引入第六种。
2. 危险动作永远是文字按钮 + 危险色，**不用实心大按钮**（避免误点）。
3. 数字与路径用等宽；中文用系统 UI 字体。
4. 每张卡上"可点的"和"只是显示的"必须一眼可分——不可点的元数据不要有任何按钮外观。

# 四、操作路线

路线 = 一个意图从进入到完成的最短路径。**步数就是这条路线好不好用的唯一指标。**

| # | 路线 | 步数 | 经过预检 | 可能被阻断 |
|---|---|---|---|---|
| R1 | **日常巡检**：唤起 → 扫用途卡 → 收起 | **0 点击**（全绿时） | 否 | 否 |
| R2 | **切换用途**：点目标组启用 → （仲裁确认）→ 等进度 | 2–3 | 是 | 是 |
| R3 | **单服务快启/快停**：展开成员 → 启动/停止 | 2 | 是（启动时） | 是 |
| R4 | **纳管新东西**：进配置态 → 新建 → 探测 → 填必填 → 准备 → 试运行 → 转正 → 入组 | 7–9 | 是（试运行时） | 是（施工态，允许长） |
| R5 | **排障**：看到异常 → 处置 → 按归因修正 → 重试 | 4–6 | 是 | 否（已在处置中） |
| R6 | **临时释放资源**：资源面 → 停某占用者 | 2–3 | 否 | 否 |
| R7 | **改配置**：配置态 → 点服务 → 改 → 保存（自动停起） | 4–5 | 是 | 是 |
| R8 | **维护组**：配置态 → 组 → 增删/排序/独占 → 保存 | 4 | 否 | 否 |
| R9 | **退出**：退出 → （有服务则确认） | 1–2 | 否 | 否 |
| R10 | **处理外部变更**：点提示条「应用」 | 1 | 否 | 否 |
| R11 | **托盘快启**：托盘右键 → 启用某用途 | 2 | 是 | 是 |

**只有 R4 允许步数多**（施工态，7–9 步可接受）；其余路线**都被压在 6 步以内**，R1 是 0 步、R10 是 1 步。

# 五、行为链路（从点击服务到离开服务）

每条链路给出：入口 · 主链 · 分支出路 · **完成判据** · 链路视觉重点 · 副作用。

## 5.A 从「服务」进入（8 条）

### 链路 1 · 看一眼就走（最轻的链路）
- **入口**：配置态清单点某行（或运行态成员点点服务名）
- **主链**：①抽屉打开（配置态默认"定义"页 / 运行态默认"运行"页）→ ②扫视 → ③`Esc` 或点外部关闭
- **分支**：无
- **判据**：无副作用，**不产生任何 Toast、不产生"已保存"之类的噪音**
- **视觉重点**：定义页六段的分段标题要能支撑"扫视"；运行页的状态区要在最上方

### 链路 2 · 查为什么失败（排障主链，分支最多）
- **入口**：运行态异常卡的「处置」，或成员行点服务名
- **主链**：①抽屉运行页 → ②状态区看到 `失败` + `就绪超时` → ③看日志尾部 → ④仍不明确 → ⑤切到记录看"上次成功是什么时候" → ⑥得出归因（依赖 intent 未就绪）→ ⑦点「先启动依赖」→ ⑧等依赖就绪 → ⑨自动重试 → ⑩状态变运行中 → ⑪处置层自动收起 → ⑫关闭抽屉 → ⑬回运行态
- **分支出路**：
  - A 归因=端口冲突 →「停掉占用者」或「换端口（建议值）」→ 重试
  - B 归因=资源不足 →「释放」→ 选候选 → 停 → 重试
  - C 归因=参数错误 →「编辑服务」→ 跳定义页并**聚焦出错字段** → 改 → 保存（含停→起）→ 回运行页确认
  - D 修不好 →「禁用（阻止反复重启）」→ 离开（避免无限重启吃资源）
  - E 只想留证 →「复制错误」/「打开目录」→ 离开
- **判据**：`lastError` 清空 **且** 状态为运行中；处置层自动收起
- **视觉重点**：归因结论第一、修正动作第二、日志第三——**不能让日志把修正动作挤下去**

### 链路 3 · 停一个服务给别的让位
- **入口**：运行态成员行「停止」，或资源面占用者「停止」
- **主链**：①点停止 → ②（若被其它运行中的组共用）提示共用者 → ③确认 → ④等进程退出与端口释放 → ⑤状态变已停止 → ⑥余量即时变化
- **分支**：A 进程已死/权限不足 →「强制停止」；B 停错了（它属于我正在用的用途）→ 该组变"部分可用" → 转入链路 8
- **判据**：端口与资源**真的释放**（不是"命令已发出"）
- **视觉重点**：可释放量要在确认前给出数字

### 链路 4 · 改一个参数并生效
- **入口**：配置态清单点行 → 定义页
- **主链**：①改字段 → ②点保存 → ③（若正在运行）提示将重启 → ④停 → ⑤起 → ⑥等就绪 → ⑦Toast「已按新参数运行」
- **分支**：A 保存后预检不通过 → 阻断 + 三条出口；B 取消 → 不保存，抽屉保持打开
- **判据**：**新参数真的在跑**——不是界面显示新参数
- **视觉重点**：保存按钮的可用条件（有改动 + 校验通过）要可见，否则用户不知道自己为什么点不动

### 链路 5 · 纳管一份新东西（施工主链）
- **入口**：配置态「新建服务」
- **主链**：①选目录/文件/粘命令 → ②**探测**给出建议形态（"这看起来是 docker 应用"）→ ③确认 → ④自动填好可推断字段 → ⑤补必填 → ⑥准备（拉镜像，带进度、可取消）→ ⑦试运行 → ⑧就绪 → ⑨转正 → ⑩加入组（新建或选已有）→ ⑪回清单
- **分支**：A 探测给不出结论 → 手动选形态 → 填必填；B 准备失败 → 处置（重试/换镜像源/换目录）；C 试运行就绪超时 → 延长等待 / 看日志 / 改判定；D 不想留 → 放弃 → 临时实例被停止并移除
- **判据**：**试运行通过**（不是"保存成功"），且下次启动不再需要我提供信息
- **视觉重点**：探测结论必须抢眼（它省掉了我判断"这是什么"的成本）；准备进度要就地，不要模态

### 链路 6 · 素材没就位
- **入口**：定义页准备段显示"模型文件缺失" / 素材面
- **主链**：①点下载 → ②模态：搜索或直链 + 可选 SHA256 → ③下载（进度、可取消）→ ④校验 → ⑤就位 → ⑥回准备段 → ⑦立即准备 / 试运行
- **分支**：A 哈希不符 → 删除损坏分片 + 报错 → 重试；B 取消 → 保留 `.part`，下次续传
- **判据**：**校验通过**且能被引用它的服务使用
- **视觉重点**：可取消必须显眼（长耗时动作的唯一出口）

### 链路 7 · 部分可用修复
- **入口**：运行态用途卡显示"部分可用 3/4" + 异常区「处置」
- **主链**：①就地展开处置层 → ②归因是某成员准备失败 → ③「去准备」→ ④准备成功 → ⑤就地重试该成员 → ⑥变 4/4 → ⑦卡变"可用"
- **分支**：该成员不再需要 →「从组里移除」→ 3/3
- **判据**：组从 `n/m` 变 `m/m`，且**其它成员没有被重启**
- **视觉重点**：部分可用必须是显眼状态——否则我只看到"没起来"，不知道已有三件在跑、占着资源

### 链路 8 · 阻止反复重启
- **入口**：处置层归因"运行中崩溃"+ 已重启 3 次
- **主链**：①点「禁用（阻止反复重启）」→ ②状态变已禁用 → ③不再自动重启 → ④离开
- **分支**：之后手动启用 → 恢复自启与重启策略
- **判据**：**重启计数停止增长**
- **视觉重点**：重启次数要在处置层显示成"3 次 / 上限 5 次"，让"快要放弃了"这件事可见

## 5.B 从「用途/组」进入（3 条）

### 链路 9 · 切换用途（事务化，最长的一条主链）
- **入口**：运行态目标用途卡的「启用」
- **主链**：①点启用 → ②预检：四族逐项 → ③发现独占冲突 + 资源不足 → ④模态只展开**占用族与资源族**（其余折成"✓ 无问题"）→ ⑤点「停掉它」并看到"预计释放 18.4 GB" → ⑥确认 → ⑦切换进度：停 OpenViking → 等端口/显存释放 → 启动 chat-27b → 等就绪 → ⑧卡变可用
- **分支出路**：A 中途点「中止并回滚」→ 恢复 OpenViking → 卡回"部分可用"；B 新档启动失败 → **自动回滚** → 提示"已恢复 OpenViking" +「处置」；C 选「强制启动」→ 按降级启动 → 结果写入运行记录（用于修正下次预检）
- **判据**：目标组**全部可用** + 被让位组**已停净**；失败时**已回滚**（不是两头落空）
- **视觉重点**：**将停谁、能释放多少**这两个数字；进度阶段要按序列出，而不是一个转圈

### 链路 10 · 维护组定义
- **入口**：配置态 → 组 → 编辑（或运行态卡菜单「编辑组」）
- **主链**：①增删成员 → ②调顺序（顺序=启动/停止序，需在界面说明）→ ③标记独占 → ④保存 → ⑤Toast → ⑥回运行态看组条更新
- **分支**：删除的成员正在运行 → 提示"组已改，是否按新定义重启该组"（否则运行态与定义不一致）
- **判据**：组的表现**与定义一致**
- **视觉重点**：必须在界面上写明"顺序就是启动与停止顺序"，否则它看起来只是个列表

### 链路 11 · 从托盘快进快出
- **入口**：托盘右键菜单
- **主链**：①选「启用 OpenViking」→ ②（可能触发预检/仲裁）→ ③Toast → ④关掉菜单（**不打开主界面**）
- **分支**：双击托盘 → 唤起主界面 → 扫一眼 → 关窗回托盘
- **判据**：用途可用，且我**没有被迫打开窗口**
- **视觉重点**：这条路线的价值就是"不打开主界面"——托盘菜单要给足信息（哪个可用、哪个在跑）

## 5.C 从「资源」进入（1 条）

### 链路 12 · 资源紧张，临时释放
- **入口**：运行态资源面
- **主链**：①看占用者按占用排序 → ②点某服务「停止」→ ③确认（显示可释放量）→ ④余量即时变化 → ⑤回「可启动清单」看现在能启动什么
- **分支**：停错服务（它属于我在用的用途）→ 该组变"部分可用" → 转入链路 7
- **判据**：**"我现在能启动什么"这个答案变了**
- **视觉重点**：占用者的**可信度标注**（实测/估算/推算）——三者混用同一视觉，比不做更危险

## 5.D 从「全局」进入（3 条）

### 链路 13 · 退出
- **入口**：界面「退出」或托盘菜单「退出」
- **主链**：①点退出 → ②（有运行中服务）确认模态：列出是哪几个 + 「同时停止」勾选（默认勾选）→ ③确认 → ④停（等真正退出）→ ⑤应用退出
- **分支**：A 不勾选 → 服务脱离应用继续运行 → 退出；B 取消 → 回界面；C **关窗**（不是退出）→ 隐藏到托盘，服务继续跑
- **判据**：服务状态**符合我的选择**，没有残留占用
- **视觉重点**：必须区分「关窗」与「退出」——这是托盘常驻应用最常被误用的一处

### 链路 14 · 外部改了配置
- **入口**：内联提示条
- **主链**：①编辑器改了 `services.json` → ②出现提示条 → ③点「应用」→ ④看差异清单（将重启哪几个）→ ⑤执行 → ⑥Toast「已重启 N 个」→ ⑦提示条消失
- **分支**：A 点「忽略」→ 提示条消失，**下次变更仍要提示**（不能把一次忽略当永久静音）；B 应用后有服务起不来 → 转入链路 2
- **判据**：运行状态与文件一致，且**未变化/未运行的服务没有被无故重启**
- **视觉重点**：**差异清单**——先给"将影响谁"，再执行

### 链路 15 · 备份与迁移
- **入口**：配置态行菜单 / 服务抽屉
- **主链**：①导出配方（JSON）→ ②（另一台机器）……
- **分支/缺口**：**导入尚未定义**——这是当前设计里一个真实的缺口：导出有了，导入没有，迁移和恢复能力是残缺的
- **判据**：导出文件能被另一台机器重建出同样的服务
- **视觉重点**：无（低频）

# 六、从这张地图里读出来的五件事

1. **交互量的绝大部分是"看"**：55 项原子行为里 **20 项无副作用**（含全部 12 项观察行为），接近四成；加上"看一眼就走"这类零点击链路，实际使用中大多数操作不产生任何确认与 Toast。所以"看得快"比"点得顺"更重要——**视觉重点的排序就是这份清单的直接产物**。
2. **只有三条链路会弹模态**：切换用途（链路 9）、退出（13）、以及删除类动作。其余的确认都是小事，不该打断。
3. **分支最多的是排障链（链路 2，5 条分支）**：它决定了处置层的信息密度上限。归因 → 修正动作 → 日志 的顺序不能乱。
4. **最长的是纳管链（链路 5，7–9 步）**：这没问题（施工态），但它必须在**配置态**里，不能渗到运行态——否则运行态每次都要背着 9 步的复杂度。
5. **发现一个真实缺口：没有导入**。有导出（链路 15）却没有导入，等于"能备份、不能恢复"。建议补上导入（探测 + 校验 + 冲突处理：重名服务怎么合并），否则迁移与换机是断的。
